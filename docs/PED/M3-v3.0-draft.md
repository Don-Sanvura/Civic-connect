# CivicConnect Project Engineering Document — M3 v3.0 working draft

**Status:** Draft for team review; not a signed or baselined PED v3.0.  
**Baseline preserved:** PED v1.0 and its requirements remain authoritative until an approved change request says otherwise.  
**Related decision:** DEC-008 remains deferred pending evidence-based technology and hosting selection.

## 1. Change impact and scope control

This branch introduces a proof-of-concept request API and candidate engineering controls. It does not silently change the baselined requirements or exclusions. Proposed implementation mappings in the M3 RTM addendum are provisional; the authoritative 40-row RTM and exact acceptance criteria must be reconciled before sign-off.

Impact areas: API/runtime, authentication boundary, request lifecycle, audit events, test automation, CI/security scanning, RTM evidence and release-readiness documentation. No database or hosting platform is approved by this draft.

## 2. Construction and implementation

The proof of concept uses Node.js built-in HTTP and test modules. The API exposes:
- `GET /health` for process health.
- `POST /api/requests` and `GET /api/requests` for request creation and listing.
- `GET /api/requests/:id` for request retrieval.
- `POST /api/requests/:id/assign` for manager/admin assignment.
- `PATCH /api/requests/:id/status` for controlled lifecycle transitions.
- `GET /api/requests/:id/audit` for manager/admin audit access.

Request input is validated; responses use structured errors and no-store headers. Requesters are restricted to their own records. Staff status updates are limited to requests assigned to their configured identity. State changes record actor, timestamp, action and request ID.

### Known construction limits
- Records and audit entries are held in memory and disappear when the process restarts.
- The token map is a local proof-of-concept mechanism, not an approved identity provider.
- The audit list is process-local, not durable or tamper-evident storage.
- Rate limiting, production logging/monitoring, persistence, migration and multi-instance consistency are not implemented.
- No real personal data should be entered.

## 3. Technology and deployment decision

ADR-013 proposes Node.js built-ins only as a measured proof-of-concept candidate. It is not final approval. DEC-008 requires a team capability audit, weighted decision matrix, compatibility assessment, storage/authentication review, free-tier hosting/cold-start/capacity evidence and a small deployed proof of concept. Record those results and team approval before committing to the runtime/hosting choice.

## 4. CI, quality and supply-chain controls

The candidate workflow runs syntax checks, automated tests, dependency audit, Gitleaks and CodeQL on pull requests and pushes to main. Dependabot is configured for npm and GitHub Actions updates. Workflow configuration is source evidence only: capture a successful run URL and commit SHA and review every alert before release.

The workflow should be reviewed for action-version pinning, least-privilege permissions and organisation policy before production use. Branch protection is configured in repository settings, not by a YAML file; verify the live rule separately.

## 5. Test strategy and verification

The candidate suite contains 25 test cases covering:
- Unit/component behaviour and input validation.
- Boundary values and equivalence partitions.
- Role/operation decision-table cases.
- Lifecycle state transitions.
- HTTP/API integration, error envelopes and authentication.
- End-to-end submit → assign → progress → resolve → audit flow.

Stable test IDs and provisional FR/NFR references are included. Exact baseline AC text is not yet reconciled, and test execution has not been independently verified in this draft. A test is not marked passed until a CI run or captured local output proves it.

## 6. Performance verification

`scripts/performance-runner.js` submits a configurable number of concurrent synthetic requests and reports successes, failures, p50, p95 and maximum response latency. The default is 25 concurrent requests. Run at least three repetitions in a documented environment, preserve raw output, and compare the p95 against the exact approved NFR threshold and test data/concurrency assumptions. No performance result or capacity claim is made here.

## 7. Security and privacy

Current controls include bearer-token authentication, role checks, requester ownership checks, request-body size limit, field validation, structured errors, no-store responses and basic security headers. These are useful proof-of-concept controls, not a production security assessment.

Before production, implement approved identity management, secret storage/rotation, durable access-controlled persistence, rate limiting, threat modelling, audit retention/integrity, backup/restore, privacy/data-retention rules and security testing. Do not use demo tokens for real accounts.

## 8. RTM and registers

See `docs/RTM/M3-RTM-addendum.csv` and `docs/RTM/M3-eight-link-traceability.md`. The eight-link chain is: stakeholder/source → requirement → acceptance criterion → approved design decision → implementation artefact → test case → execution/defect evidence → release decision. All 40 baseline requirements must be reconciled against the authoritative RTM without renumbering IDs.

AI-assisted draft work is recorded as AI-007 with human verification pending. Team members must append to existing risk, defect, technical-debt and decision records rather than replace registers or invent completed checks. The register update checklist identifies the outstanding actions.

## 9. Release readiness

**Current recommendation: NOT READY.** Mandatory evidence not yet present in this branch includes:
1. Successful CI, test, dependency, secret-scan and CodeQL results.
2. Two non-author PR approvals and confirmation of enforced branch protection.
3. Team-approved DEC-008 stack/hosting decision.
4. Complete 40-requirement RTM reconciliation and review.
5. Staging deployment URL, deployed SHA, health check and smoke-test output.
6. Repeated performance results compared with the approved NFR threshold.
7. Updated and reviewed risk, defect, technical-debt, ADR and AI usage registers.
8. PED v3.0 review/sign-off and named release decision.

Do not deploy this in-memory/demo-token proof of concept to real users. The release owner must update the release summary with actual evidence and accepted residual risks; this document alone does not authorise release.
